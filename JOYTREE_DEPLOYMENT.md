# Deploying to JoyTree

**This file is new as of this assembly.** No deployment documentation
existed in any earlier phase of this project — Phases 1 through 4 were
each delivered as an app-specific delta bundle (the original Phase 1
`composer.json` says so explicitly: "This is the delta to merge into the
composer.json produced by `laravel new`"). This is the first time the
project has been assembled into one complete, standalone Laravel 11
application with the full framework skeleton (`artisan`, `public/`,
`storage/`, full `config/`, `bootstrap/providers.php`,
`routes/console.php`, `phpunit.xml`, `tests/TestCase.php`, `Dockerfile`,
`.dockerignore`) included.

**Nothing in this assembled package has been executed.** This sandbox has
no PHP runtime, no Composer, and no network access — confirmed again
immediately before this assembly. Every file here was hand-written to the
correct Laravel 11 structure from source knowledge, not generated by
`laravel new` + `composer install` and then verified to boot. Treat first
boot as a real test, not a formality — see the verification checklist at
the end of this document.

## What's actually in this package

- Full Laravel 11 skeleton: `artisan`, `public/index.php` +
  `public/.htaccess`, `bootstrap/app.php` (already customized for this
  app's `role:` middleware and `/up` health route) + `bootstrap/providers.php`,
  `routes/web.php` (all four phases) + `routes/console.php`, complete
  `config/` (10 files: `app`, `auth`, `cache`, `database`, `filesystems`,
  `logging`, `mail`, `queue`, `services`, `session`, plus this project's
  own `firebase.php`), `storage/` directory tree with the standard
  `.gitignore` placeholders, `phpunit.xml`, `tests/TestCase.php`.
- All Phase 1–4 application code: every model, controller, policy, form
  request, service, migration, view, factory, and test built across the
  four phases (see `PHASE2.md`, `PHASE3.md`, `PHASE4.md` for what's in
  each).
- `Dockerfile` + `docker-entrypoint.sh` + `.dockerignore` — new, described
  below.

## What's deliberately NOT in this package

- **`vendor/`** — never generated, since that requires running Composer
  against the real internet to download packages. The Dockerfile's build
  stage runs `composer install` itself during the image build.
- **`composer.lock`** — same reason: a real lock file requires resolving
  exact package versions from Packagist, which needs network access this
  sandbox doesn't have. The Dockerfile tolerates its absence
  (the Dockerfile's vendor stage only `COPY`s `composer.json`, so a
  missing lock file can never break the build — it just means Composer
  resolves fresh versions instead of pinned ones), but **you should run
  `composer update` once, locally or in CI, and commit the resulting
  `composer.lock`** so every future build uses identical package versions
  instead of "whatever's newest today."
- **A real `.env`** — only `.env.example` is included, as it should be.
  Never commit a real `.env` with production secrets.

## Fixed while assembling this package

Two real inconsistencies surfaced only now that the full skeleton exists
to check against:

1. **`bootstrap/app.php` referenced `routes/console.php`, which never
   existed.** Would have caused a fatal error the moment Artisan tried to
   boot. Created it (standard Laravel default — just the `inspire`
   command).
2. **The old `.env.example` set `SESSION_DRIVER=database`,
   `CACHE_STORE=database`, and `QUEUE_CONNECTION=database`, but no
   migration for `sessions`, `cache`, or `jobs` tables exists anywhere in
   Phases 1–4.** This would have thrown a "table not found" error on the
   very first request. Changed the defaults to `file`/`file`/`sync`
   (documented in each config file), which need no additional tables.
   Added a `password_reset_tokens` migration since `config/auth.php`
   references that table by default even though no password-reset UI has
   been built yet in any phase.

## The Docker setup

`Dockerfile` is a two-stage build:
1. A `composer:2` stage installs production dependencies.
2. A `php:8.2-apache` stage copies in the app + `vendor/`, enables
   `mod_rewrite`, points Apache's document root at `public/` (Laravel's
   web root — never any other directory), installs the PHP extensions
   this app actually uses (`pdo_mysql` for the authoritative MySQL store,
   `gd`/`exif` for student profile-photo uploads, `zip`/`bcmath`/`mbstring`/
   `xml` for Composer dependencies including `kreait/firebase-php`), and
   sets `storage/`+`bootstrap/cache` writable by the web server user.

`docker-entrypoint.sh` runs once per container start, **before** Apache:
generates `APP_KEY` if unset, caches config/routes/views, runs
`php artisan migrate --force`, and links `public/storage`. Then it hands
off to `apache2-foreground` — **`php artisan serve` is never used.**

The container's `HEALTHCHECK` hits `/up` — Laravel 11's own default
health-check route, already wired in `bootstrap/app.php`
(`health: '/up'`). **Note on the literal path:** the earlier Phase 4
instructions said "keep the `/health` endpoint," but no route at that
exact path has ever existed in this project — the actual, working
endpoint has always been `/up`. I kept `/up` rather than silently
introducing a second, different health route. If JoyTree's platform
specifically expects a request to `/health` to succeed, tell me and I'll
add a one-line alias route (`Route::get('/health', fn () => response('OK'))`)
— that's a trivial, safe addition, but I didn't want to guess at inventing
a second endpoint's behavior without you confirming it's actually needed.

Auto-migrating on every container boot is a pragmatic default for a
single-container deployment. If you'd rather control migrations manually
(e.g. during a rolling multi-instance deploy), remove the
`php artisan migrate --force` line from `docker-entrypoint.sh` and run
migrations as a separate, deliberate step instead.

## Environment variables to set on JoyTree

At minimum:
- `APP_KEY` — generate once (`php artisan key:generate --show`) and set
  it as a fixed variable; don't let it regenerate on every deploy, or
  every existing session and any encrypted data becomes unreadable.
- `APP_URL` — the real deployed URL (affects `storage` disk URLs and
  generated links).
- `DB_HOST`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` — MySQL,
  the authoritative store for all school data across every phase.
- `FIREBASE_PROJECT_ID`, `FIREBASE_CREDENTIALS`, `FIREBASE_DATABASE_URL`
  — only needed once a future phase actually uses Firebase for real-time
  features; nothing in Phases 1–4 reads them yet (see `config/firebase.php`).

## First-deploy checklist (please actually run this)

Since nothing here has been executed by me:

1. `composer install` (or let the Docker build do it) — confirm it
   completes without errors, then commit the resulting `composer.lock`.
2. `cp .env.example .env` and fill in real values; `php artisan key:generate`.
3. `php artisan migrate` — confirm all 23 migrations run cleanly against a
   real MySQL database (not just SQLite in tests).
4. `php artisan db:seed` (optional) — confirm the sample data from
   `DatabaseSeeder.php` loads without error.
5. `php artisan test` — confirm the full suite actually passes. Every
   phase's report in this project has said tests were statically traced,
   never executed, because this sandbox can't run PHP. This is the first
   real chance to find out if that tracing was accurate.
6. `php artisan storage:link` — confirm `/storage` resolves and a
   student profile-photo upload actually round-trips.
7. Log in as each of the three seeded roles (admin/student/parent) and
   click through each phase's manual-testing checklist in `PHASE2.md`,
   `PHASE3.md`, and `PHASE4.md` — none of those checklists have been
   walked through against a live instance either.
